# План доработки проекта

Работаем пошагово: для каждого шага сначала описание, выбор технологии
и сравнение с аналогами → подтверждение → код с построчным объяснением.

Статусы: ⬜ не начато · 🟨 в работе · ✅ готово

## Шаг 0. Рабочее окружение ✅
- WSL2 + Ubuntu 20.04 + ROS Noetic + Gazebo 11 (GUI через WSLg).
- Проверка: исходный проект собирается и запускается «как есть».

## Шаг 1. Рефакторинг на ROS 1 🟨
1. ✅ Гигиена репозитория: `.gitignore`, флаги исполняемости, переименование
   `my_robot_simulation_control-main` → `my_robot_simulation_control`,
   удаление `old_files` (история остаётся в git), относительный путь в `my_map.yaml`.
   Проверено в Gazebo: поведение как в `BASELINE.md`.
2. 🟨 Ядро без ROS (`warehouse_core`): сетка, A*, выбор робота для задачи —
   обычный Python, тесты на pytest (запускаются и на Windows).
   Алгоритмы переносятся как есть, вместе с ошибками; тест сверяет с исходным кодом.
   Узлы переключаются на ядро уже при переходе на ROS 2.

## Шаг 1А. Переход на ROS 2 Jazzy + Gazebo Harmonic ⬜
- Ubuntu 24.04 в WSL2, `colcon`, `rclpy`, мир склада и робот в новом Gazebo,
  `ros_gz_bridge` для привода и лидара.
- Сюда же перенесены бывшие подшаги рефакторинга — сразу в версии для ROS 2:
  - один параметризованный узел вместо 10 копий (параметр `robot_id`,
    пространства имён), один launch-файл с числом роботов как аргументом;
  - карта из файла через `nav2_map_server` вместо массива в коде;
  - actions ROS 2 вместо перезапуска узлов через `roslaunch.scriptapi`
    и «рукопожатий» на флагах `Bool`; при ошибке задача переназначается.
- Узлы — тонкие обёртки над `warehouse_core`.
- Критерий: поведение как в `BASELINE.md`. Плагина лифта в новом Gazebo нет —
  на этом шаге лифт делается минимально (как было), полноценно — в шаге 4.

## Шаг 2. Исправление A* ⬜
- Стоимость диагонали, возврат при «путь не найден», дубль цели, граница `>= 0`,
  `heapq` вместо сортировки. Планирование по реальной карте 0.05 м с раздуванием
  препятствий (inflation) на радиус робота.

## Шаг 3. Плавное движение ⬜
- Pure Pursuit (одновременно `v` и `ω`), сглаживание пути,
  ограничение ускорения на `cmd_vel`.

## Шаг 4. Лифт: согласованная работа и две двери ⬜
- Проходная кабина: двери с двух сторон (заезд с одной, выезд с другой — без разворота).
- Свой контроллер лифта вместо стандартного плагина с таймером дверей:
  конечный автомат «вызов → приезд → открыть дверь A → ждать, пока робот заедет →
  закрыть → ехать → открыть дверь B → ждать, пока выедет → закрыть → свободен».
- Очередь вызовов, action-интерфейс `Ride(robot_id, from_floor, to_floor)`.

## Шаг 5. Движение без столкновений ⬜
- Координированное планирование: Prioritized Planning → CBS,
  таблица резервирования «ячейка × время», учёт срочности задач.
- Локальная страховка: ORCA/RVO вместо правил по секторам лидара.
- Сравнение до/после через `analyse_*.py`.

## Шаг 6. Сервер заявок ⬜
- REST API (FastAPI) + БД, связь с ROS через узел-шлюз/rosbridge.

## Шаг 7. Клиентская платформа ⬜
- Веб-интерфейс: карта склада с роботами в реальном времени,
  статусы заявок, создание заявки.

Шаги 2–7 выполняются уже на ROS 2. На шагах 3 и 5 свой контроллер
можно сравнить с готовыми из Nav2.
